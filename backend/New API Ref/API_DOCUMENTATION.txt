RUNNING VERSION
---------------
Open GET /v1/health on the server you want to identify. The response includes
version from that deployed package.json and tag as v followed by that version.
The public response omits the Git commit. Version metadata is also included when
the DB probe returns 503. Cache-Control:no-store prevents stale health/version
results. A startup/configuration failure can still prevent the application health
route from initializing. The tag is a package release label; use private hosting
or process metadata to identify the exact deployed commit because multiple commits
can share a version and tag. GET / returns 403 with ACCESS_DENIED and a
generic "Direct access is not allowed." message; HEAD / has no body. It does not
query the database or replace authentication on protected API endpoints. VPS
Nginx needs an exact location = / proxy; retain the existing HTTPS configuration.
Pushing a Git tag or commit does not mean it is live: compare the health response
with the desired release, or inspect Vercel's Current Production deployment Source.
Backend publishing is Git-only; deployment is performed by the user.

QUICK START / ENVIRONMENTS
--------------------------
Node >=24. From mss-backend: npm ci; copy .env.example to .env privately.
Configure a reachable PostgreSQL database with migrations 001..015 and runtime
grants. Do not put migration-owner credentials in the HTTP application environment.
Run npm run db:migrate only with intended migration credentials on the intended DB;
it changes schema. It is not part of routine documentation/test generation.
Start local API with npm run dev (watch + auto docs) or npm start.
Defaults: HOST=127.0.0.1, PORT=3000. Local origin http://127.0.0.1:3000.
Android emulator origin: http://10.0.2.2:3000. Physical device: reachable development
LAN host/port configured by the operator. Device localhost points to the device.
Production API origin: https://mssapi.msmeschemes.org.
All documented paths already contain /v1: never append /v1 twice.

Configuration names (actual values belong only in private environment/secret store):
- NODE_ENV, HOST, PORT: environment, bind address, listen port.
- DATABASE_URL OR DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD: PostgreSQL connection.
  DATABASE_URL takes precedence. DB_PORT default5432; pool max10, connect timeout3s,
  statement timeout10s, idle timeout30s, idle transaction timeout15s.
- DB_SSL (or DATABASE_SSL), DB_TLS_VERIFY, DATABASE_CA_FILE: database TLS.
  Production requires TLS. Keep certificate verification true and configure CA.
  Code supports explicit temporary DB_TLS_VERIFY=false with DB_SSL=true; this
  encrypts but does not verify DB identity and is not a production assurance.
- CORS_ORIGINS: comma-separated exact web origins, no wildcard. Production HTTPS.
  Native mobile requests do not rely on CORS for authentication.
- TRUSTED_PROXY_CIDRS: actual trusted proxy IPs/CIDRs only; empty means no proxy trust.
  Never trust every address or arbitrary forwarded protocol headers.
- VERCEL=1 is a server deployment flag used for exact forwarded-HTTPS recognition;
  never derived from caller input. Production HTTP requests receive426 HTTPS_REQUIRED.
- GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET: server-only provider configuration.
- SARVAM_API_KEY: server-only speech/chat credential; never a Flutter define or URL.
- GOOGLE_REDIRECT_URI: exact registered callback ending /v1/auth/google/callback.
  Use the configured local port (3000 by default); production callback must be HTTPS.
- AUTH_APP_REDIRECT_URI: approved app callback, default
  com.inschemes.app://login-callback/; configure Flutter deep links to match.
- LEGAL_DOCUMENT_VERSIONS: JSON mapping terms,privacy_policy,privacy_notice,consent
  to actual published versions. Missing configuration blocks final legal onboarding.
- MIGRATION_DATABASE_URL: privileged migration CLI only; never mobile configuration.
No endpoint returns server configuration secrets, database connection settings or
role credentials. Authentication endpoints return session credentials only to the
authenticating client.

SHARED HTTP CONTRACT / SECURITY
-------------------------------
JSON requests: Content-Type: application/json; Accept: application/json.
Owner calls: Authorization: Bearer <latest opaque Node access token>.
Tokens are opaque 43-character base64url credentials, not JWT authorization claims.
Do not send a client user_id to select ownership; it comes from the authenticated
session. Owner database access uses transaction-local identity + RLS policies.
Admin endpoints additionally check mss.user_roles. Production startup rejects unsafe
DB owners/superusers/BYPASSRLS/role-creation/schema-creation privileges.

JSON limit64KiB generally; authenticated scheme upload10MiB; all other scheme
administration JSON bodies600KiB (including draft writes and publication requests).
Compressed request bodies are not accepted. Write helpers reject
unknown top-level fields; profile/business validation allowlists nested fields.
GET scheme bodies are explicitly rejected; all other GET callers should omit body.
Do not assume all read endpoints reject every unused query key: strict per-route
validation is specified in each entry. JSON {} differs from an absent request body.
Response shapes are endpoint-specific; there is no universal data envelope.
Most empty paginated feeds return200 with items:[] and next_cursor:null.
Admin draft listing uses items only; paginate with after=<last-id> until empty.
204 and304 have no JSON body. Legacy bundle download is raw application/gzip bytes.
Private responses use no-store. Public catalog has documented ETag/cache behavior.
X-Request-ID is generated server-side. It is a response HEADER, not a guaranteed
JSON field. Current errors: {"error":"CODE"}, optionally details. Version conflicts
use details:[{"field":"version","current":2}]; draft conflicts return the code only.
No global message/request_id/data envelope. Health failure has its own body shape.
Unexpected failures are500 INTERNAL_ERROR. Hosted startup failure503
SERVICE_UNAVAILABLE may occur before application request headers are initialized.
Parser errors:400/413/415 INVALID_REQUEST. Write media errors415 JSON_REQUIRED.
Unknown URL/method combinations return404 NOT_FOUND. Production HTTP426 HTTPS_REQUIRED.
Never log body, query, auth headers, exception stacks, SQL or personal identity.
Retain safe status/request ID for troubleshooting. Existing fixed security/startup
events are intentional operational logs, not disposable debugging output.

Quotas: global120/minute/IP (health bypass); /auth additionally20/minute/IP local
and30/minute/IP database-backed (including password login/logout operations).
Password login has separate10/minute/IP and10/minute/normalized-email quotas;
these are independent buckets, not an IP/email pair. Owner password5/minute/owner.
Profile60/minute/owner; inbox/SSE/push devices share60/minute/owner; schemes
60/minute/owner. Admin security/notification routes share20/minute/owner;
scheme administration has a separate20/minute/owner quota.
Account deletion has its own3 attempts/minute/owner quota, in addition to global limits.
Favorites/eligibility results share60 requests/minute/owner (LIBRARY_RATE_LIMITED).
Support guest10/minute/IP; support submission has additional hourly/cooldown rules.
429 responses supply Retry-After seconds; honor it. If an intermediary strips the
header, use bounded exponential backoff with jitter.
Shared quota-store outage503 AUTH_TEMPORARILY_UNAVAILABLE fails closed.
Applicable module quotas are cumulative.

Shared owner/admin errors:401 UNAUTHORIZED for missing/invalid/expired bearer;
403 FORBIDDEN for insufficient admin role. Owner quota codes include
PROFILE_RATE_LIMITED, NOTIFICATIONS_RATE_LIMITED, SCHEMES_RATE_LIMITED,
LIBRARY_RATE_LIMITED and PASSWORD_RATE_LIMITED. Admin security/notification quota:
AUTH_RATE_LIMITED; scheme administration quota:SCHEME_ADMIN_RATE_LIMITED.
Global/local auth quota code:RATE_LIMITED. Their HTTP status is429. Request parser,
media and transport errors above apply before endpoint validation where relevant.

SHARED SCHEMAS
---------------
ProfileAggregate: id/email/photo_url; all writable fields below; business|null;
legal_acceptances:[{document_type,document_version,accepted_at}]; version integer;
created_at/updated_at ISO8601; is_profile_complete boolean; missing_fields:string[].
email/photo_url are provider-derived; last_login is not an editable profile field.
All fields present in response. Nullable unanswered fields remain null, never
fabricated defaults. annual_income and business funding are JSON numbers, not strings.

Writable profile fields (unknown keys rejected):
- name: trimmed nonempty string<=150, not nullable.
- gender<=50; state/district/city/community/religion/education_level/qualification/
  applicant_type/disability<=150; house/area<=255: nullable strings.
- phone: null or exactly10 digits. pincode: null or exactly6 digits.
- Never silently truncate phone/pincode to satisfy length. Normalize known phone
  formatting/country code deliberately, then validate; reject an invalid pincode.
  For draft saves omit an unanswered/invalid field, or send null only to clear it.
- dob: null or real YYYY-MM-DD, year>=1900, not future.
- annual_income: null or nonnegative JSON number<=9999999999999.99, at most2 decimals.
- first_gen_graduate/veteran: nullable booleans. notifications: non-null boolean.
- language: en|ta (profile does not accept hi although schemes support hi).
- theme: light|dark|system; navigation_mode: regular|companion; non-null enums.
Text disallows markup brackets and control characters; strings trimmed.
applicant_type is free text, not an enum: Student and Individual are accepted
examples, not an exhaustive list. Maximum150 characters; a nonempty value is
required for onboarding completion. The server does not convert employment status
into an applicant category; the frontend owns that mapping. The sample Individual
does not restrict accepted values. email/photo_url are response-only identity data;
exclude them from profile PATCH and onboarding writes.
Omitted PATCH keys unchanged; false,0,null intentional. At least one field required.
Profile GET lazily creates owner row with identity name. Defaults: notifications=true,
language=en,theme=light,navigation_mode=regular. User identity UUID is preserved.
Completion requires name,dob,gender,phone,state,district,city,house,pincode,
applicant_type,education_level,community,annual_income and all four current consents.
An active student business without registration/funding/registration_numbers can
fail business.STUDENT_WITHOUT_VENTURE. A business is optional: explicit null allowed.
Specifically, applicant_type Student (case-insensitive after trimming) with a
business object, business_registered:false, funding_required_amount:0 and empty
registration_numbers adds business.STUDENT_WITHOUT_VENTURE to missing_fields.
Onboarding then returns400 ONBOARDING_INCOMPLETE with that field in details.
Use business:null only when there is no business to retain: it deactivates an
existing active business as part of a successful onboarding transaction.

Incomplete onboarding: save valid available profile fields with PATCH /me/profile
using the latest X-Profile-If-Match, and keep onboarding pending. annual_income:0
is valid and must not be treated as missing. Use response missing_fields as the
server's completion checklist, including current legal acceptances. Log missing
field names only, never entered personal values. A successful draft PATCH does
not itself prove onboarding is complete; check returned is_profile_complete.

Business (all keys required when not null):
{ "profile_name":"Example venture", "industry":"Manufacturing",
  "applicant_type":"Individual", "business_stage":"Idea",
  "business_registered":false, "funding_required_amount":0,
  "registration_numbers":"", "is_first_generation_entrepreneur":true }
profile_name/industry/applicant_type: trimmed nonempty<=150.
registration_numbers: trimmed string<=500, empty allowed, not null.
business_stage: Idea|Prototype|Registered|Operational|Expansion.
Both flags boolean; funding amount same numeric rules as annual_income, not null.
Response adds id,user_id,is_active,created_at,updated_at. Only active business
included. Legal document types: terms|privacy_policy|privacy_notice|consent.

Concurrency: retain quoted ETag from GET/updated profile and send
X-Profile-If-Match: "profile-<version>" for PATCH/onboarding/acceptance writes.
If hosting weakens the response ETag to W/"profile-<version>", that exact
spelling is also accepted in X-Profile-If-Match for the same current version.
Wildcards, lists and stale versions are not accepted. This compatibility does
not apply to the standard If-Match header, which still requires a strong tag.
Standard If-Match is accepted by application but may be intercepted by hosting;
prefer X-Profile-If-Match on Vercel. Conflicting dual headers400. Missing428,
stale412 (details include current version). Never blind-retry stale writes.

SchemeSummary fields: id,name,short_name|null,category|null,source_category|null,

CLIENT INTEGRATION / WORKFLOW OVERVIEW
---------------------------------------
Integration guidance only: this change does not modify Flutter application code.
Use a configured origin with no trailing /v1. All endpoint paths here include it.
Use secure platform credential storage; never preferences/plaintext/logs for tokens.
One API client/session manager should own token refresh, mutation versioning and
401 handling. Account identity comes from /me; editable data from /me/profile.

Node authentication and storage boundary:
- These Node endpoints store identity/profile/session data in the configured
  PostgreSQL database under schema mss. They do not create a Supabase Auth session
  or mirror records to a separate Supabase service. Any direct Supabase calls in
  a frontend are a separate integration, not part of this API's save guarantee.
- POST /v1/auth/google/start accepts only {code_challenge}. POST /v1/auth/exchange
  accepts only {code,code_verifier}. Do not send redirect_uri to either operation;
  redirects are configured on the server. Unknown body keys return400 INVALID_REQUEST.
  /v1/auth/google/exchange and /v1/me/profile/draft are not registered endpoints.
- A successful Google callback upserts provider email/name/subject in mss.users.
  A successful app-code exchange creates the Node session and returns tokens/user.
  Confirm that exchange succeeded, then GET /v1/me with its Node bearer. A Google
  account selection, app redirect or visible profile form alone is not confirmation.
- GET /v1/me/profile creates/reads mss.profiles. PATCH saves valid draft fields;
  it does not save business or legal acceptances. Node identity uses mss.users,
  not public.users or a separate Supabase auth.users table.
- Final PUT /v1/me/onboarding requires a nonempty writable profile object,
  business object or explicit null, and legal_acceptances containing1..4 current
  records (not an empty array). Completion checks all four current document types
  across stored and submitted acceptances. Fetch versions from /me/legal-documents
  and collect agreement; a local consent checkbox alone does not record acceptance.
- Keep the final screen pending on any non-2xx save response. Mark onboarding
  complete only after a successful save response with is_profile_complete:true;
  retain its aggregate and ETag. A local cache write or successful draft PATCH
  with missing_fields does not confirm completed cloud onboarding.

1. Generate PKCE verifier/challenge -> /auth/google/start -> external browser ->
   server callback -> approved app deep link -> /auth/exchange -> secure token pair.
2. Cold start: restore token pair, GET /me; refresh single-flight if expired.
   Rotation consumes old credentials; don't retry with a consumed refresh token.
3. GET /me/profile and /me/legal-documents; PATCH drafts or PUT full onboarding
   with current version/idempotency key. Missing legal versions need server setup.
4. Save profile state before scheme requests. Use list/detail/application/related
   for online browsing. For the release check and complete offline download,
   follow FRONTEND SCHEMES SYNC CONTRACT below; it is the detailed sync sequence.
5. /promotions can run anonymously or after profile save for audience selection.
6. Inbox -> /me/notifications; subscribe to /me/notifications/events for SSE hints;
   refetch list/count after events. FCM registration enables background push hints.
7. Support: existing bearer OR guest-session -> guest token; persist one UUID
   Idempotency-Key for retries of one submission. Do not send both identities.
8. Optional local password setup/change/remove requires recent authentication;
   success revokes all sessions and requires fresh sign-in.
9. Logout/revoke session clears tokens, subscriptions and private offline data.
10. Delete account: DELETE /v1/me with bearer, no query/body. Requires authentication
    within5 minutes, not merely a refreshed token. On403 reauthenticate explicitly;
    on204 clear private device data and remain signed out. This is a permanent
    Node account deletion, not logout. Google and unmigrated external data are
    outside its scope. Do not automatically sign in after a lost delete response.
11. Saved favorites: GET /me/favorites to restore canonical IDs; PUT
    /me/favorites/:id with no body to save; DELETE same canonical ID to remove.
    Read pages using limit/cursor. References can survive state/availability changes;
    content still follows scheme API permissions. Max500 favorites per owner.
12. Eligibility persistence: GET /me/eligibility-results, retain ETag; PUT exactly
    {"scheme_ids":["<visible-scheme-id>"]} with X-Eligibility-If-Match. Empty []
    clears. Versioned replacement prevents lost updates; on412 reload/reconcile.
    This stores client results, not server-certified eligibility. It does not
    modify favorites and is read separately from ProfileAggregate.
    Offline writes are queued locally and replayed online with current identity,
    state and version. Never reuse a previous account's queue or silently overwrite.
Catalog OTA is a separate public legacy bundle flow, not the state schemes dataset.
Apply links open official websites; application submission is outside these APIs.

CLIENT TRANSPORT RULES
-----------------------
Use each entry's method, URL, headers and sample body with the frontend HTTP client.
Retain status and headers (ETag, Retry-After, Idempotency-Replayed, Content-Encoding)
and inspect status/media before decoding. For204/304 skip JSON parsing.
Legacy application/gzip downloads are compressed files: verify the compressed
package hash/size against the legacy manifest before decompression. Schemes sync
is application/json with negotiated Content-Encoding:gzip: an HTTP stack may
already decompress it. Decode exactly once; no package hash is supplied for sync.
Use dynamic JSON decoding for heterogeneous scheme documents/fees/deadline; do not
force all values into strings. Preserve snake_case keys and snake/camel distinction
between catalog/current and raw release manifest.
OAuth callback is a browser navigation, not a Flutter JSON request.
For a guest call omit Authorization and set X-Support-Guest; optional bearer promotion
calls may omit token entirely. Never attach revoked tokens to public requests.

TESTING / DEPLOYMENT LIMITS
---------------------------
npm test: generates docs first; runs unit, local HTTP, docs parity/contract tests.
npm run docs:check: read-only deterministic comparison; fails on missing metadata,
invalid declared tables, duplicate route definitions or stale generated reference.
npm run format:check: formatting. npm run catalog:check: local source dry-run.
npm run db:tables: read-only expected-table existence probe (no credentials printed).
DB/HTTP workflow verification scripts require explicitly configured test DB and may
insert/delete synthetic fixtures, create temporary schemas or import test data:
auth:verify,profiles:verify,security:verify,catalog:verify,notifications:verify,
support:verify,promotions:verify,schemes:verify. Read scripts before selecting DB;
account:verify requires an explicit ACCOUNT_TEST_DATABASE_URL; there is no fallback
to the configured application database. It creates disposable schema/role fixtures
in the selected test environment and verifies actual FK cascades/RLS/HTTP behavior.
do not run indiscriminately on production. db:migrate/import/publish mutate state.
Postman collections in docs/postman are supplementary smoke tools, not the master
contract. Their environment variables contain placeholders only. Never share filled
credential environments or persist live responses containing tokens.
Local tests cannot certify current live OAuth consent, deployment, real device
deep-link behavior, provider quotas, production data integrity or performance load.
Use restricted-role PostgreSQL/RLS fixture checks and staged HTTP smoke tests before
production promotion. No claim of production readiness follows from docs generation.
Historical review results are recorded in
docs/backend-maintenance-review-2026-10-18.txt. They describe that review's schema
and configured login, not the current migration inventory or deployment status.
Use current db:tables/security probes in an authorized environment to assess the
actual rollout. Provision restricted runtime credentials and verified DB TLS.
Account-delete addition requires migration012 and runtime DELETE permission on
mss.users (deployment/account-deletion-runtime-grants.sql). Child removal uses FK
cascades; no broad support DELETE privilege is granted. The endpoint checks the
support FK before deletion so an old SET NULL schema cannot silently retain PII.
Future owner tables must have reviewed deletion semantics before API publication.
Delete-account code/tests/docs are not an assertion that migration012 is deployed.
Saved-library addition requires migration013_saved_library.sql plus
deployment/saved-library-runtime-grants.sql before deploying the new routes.
New favorites and eligibility_results tables both FORCE RLS and cascade from users,
so account deletion also removes these private sets. No catalog/profile data is
rewritten by this migration. New routes are source/test-ready, not live-certified.

DOCUMENTATION WORKFLOW / SINGLE REFERENCE
-----------------------------------------
API_DOCUMENTATION.txt is generated from actual registered application routes,
docs/api/contracts.mjs (reviewed semantics/examples), this integration text,
current source errors, SQL-table references, validation source references and fingerprints.
Only currently registered operations are emitted; deleted routes disappear.
A new or renamed route without complete metadata fails generation instead of
inventing an undocumented contract. Add its descriptor alongside implementation.
When changing behavior, update its descriptor/examples in the same change.
Automation cannot infer the business meaning of arbitrary code: reviewers must

NOTIFICATION REALTIME + PUSH - HOW IT WORKS
------------------------------------------
Backend producer -> committed notification -> DB trigger -> owner event log and
durable device outbox -> SSE client / separate FCM worker -> authenticated inbox.

1. Apply migration014_notification_delivery.sql AFTER earlier migrations. Apply
   deployment/notification-delivery-runtime-grants.sql as the database administrator.
   HTTP runtime gets owner-scoped event/device reads, registration-broker EXECUTE,
   admin-routed notification INSERT and idempotency receipts, not push-job access.
   Provision a separate restricted login with mss_push_worker membership.
   Production HTTP startup rejects membership in the worker group as well as
   table ownership/superuser/DDL privileges. Never combine the two login roles.
   Production worker/cleanup startup also requires the restricted worker membership
   and rejects table ownership/superuser/DDL privileges.
2. Enable FCM HTTP v1 in the Firebase project; give the server service account send
   permission. Configure Application Default Credentials (e.g.
   GOOGLE_APPLICATION_CREDENTIALS pointing outside the repository). Set FCM_PROJECT_ID
   and PUSH_TOKEN_ENCRYPTION_KEY: secret base64-encoded32 random bytes shared by HTTP
   registration and worker. Never document its value or service-account JSON.
   No legacy server key/admin secret belongs in Flutter.
3. Worker-only PUSH_DATABASE_URL selects the restricted worker login; use verified
   DB TLS in production. Run npm run push:work as a supervised separate process,
   or npm run push:work -- --once from a suitable scheduler. Claims4 jobs/batch with
   SKIP LOCKED,60s recoverable leases; idle loop1s. HTTP starts no background daemon.
   Without the worker inbox/SSE work, but no background push leaves the queue.
4. Flutter team configures Firebase Messaging, obtains OS notification permission,
   receives SDK registration token and PUTs /me/push-devices/:id with a local UUID
   and Node bearer. Re-register on SDK token rotation/fresh login. iOS needs APNs
   setup and app capabilities. Endpoint supports android/ios only. This backend
   does not modify mobile code or grant OS permission. Follow current SDK docs.
5. Staff publishes POST /admin/notifications using a persistent idempotency UUID.
   Committed INSERT creates owner-ordered event + job per active-session device.
   No registration means no job; app can still fetch inbox. Registration never
   sends old notification history. Read/delete changes emit hints, not new pushes.
6. Foreground SSE polls committed events2s, heartbeat10s, bounded stream~25s.
   Reconnect with jitter1..5s and Last-Event-ID using a streaming HTTP client.
   ready/reset/change hints require REST inbox/count refresh. Persist cursor AFTER
   handling/refetch. Session/token rechecked each poll; logout/refresh/expiry closes
   the old stream. Expired7-day history returns reset/full refetch. Concurrent
   processes use committed per-owner sequence ordering, not a process-local bus.
   Limits50 streams/process,2/owner plus shared notification quota60/minute. Disable
   proxy buffering; test actual host streaming/timeouts. Push/SSE can overlap, so
   deduplicate by notification_id. Cancel stream on background/logout.
7. Background worker checks generation, active session, unread state and current
   profiles.notifications before each send. false suppresses push, not inbox/SSE;
   absent profile uses existing true default. FCM payload: generic MSS/new-update
   notification plus inbox UUID only. Full text is fetched with current owner auth.
   Wrong-account clients cannot fetch private content. No automatic scheme-change
   campaign exists: a trusted backend producer must choose recipients/message.
8. UNREGISTERED removes only matching device generation.429/5xx/network/auth errors
   back off from60s with jitter/Retry-After, max8 attempts/24h job age. Other provider
   rejections become dead jobs. FCM TTL1h. Acceptance does not prove display/viewing.
   At-least-once delivery can duplicate after a send/ack crash; UUID/collapse/tag
   support deduplication. Do not delete tokens on every400; UNREGISTERED is specific.
9. Logout/session revocation removes session devices/jobs; account deletion cascades
   all new private tables. Already accepted/in-flight generic pushes cannot be
   recalled. Re-registering the same physical token to a new authenticated account
   atomically transfers it and removes old queued jobs. Device IDs alone cannot
   transfer foreign tokens. Stable encryption key required; plan key rotation and
   re-register/re-encrypt devices rather than silently changing it.
10. Schedule npm run push:cleanup daily with worker-only credentials: event retention
    7days, completed/dead jobs7days, expired/revoked session devices removed. Keep
    event sequence heads monotonic. Publish receipts remain until actor/recipient
    account deletion so retries do not recreate a deleted inbox notification.

UNIFIED SCHEME RELEASE WORKFLOW
-------------------------------
Authoritative data: mss.scheme_records and its localizations/aliases/relations.
Published reads continue to use FORCE RLS and the token owner's saved profile
state. Drafts never replace a published row until an approved publication commits.
IDs are retained on withdrawal; favorites and saved references are not deleted.
There is no full-replacement upload mode. Omitted schemes remain unchanged.

Staff sequence (all admin requests use Authorization:Bearer <access-token>):
1. POST /v1/admin/schemes/uploads with Content-Type:application/json and a stable
   Idempotency-Key:example-upload-key-0001. An explicit upload example:
   {"schema_version":1,"mode":"partial","collections":[{
     "collection":"tamil_nadu","meta":{"count":1},"schemes":[{
       "id":"TN2026-001","level":"state","state":"Tamil Nadu",
       "name":{"en":"Example scheme","ta":"சோதனை திட்டம்"},
       "status":{"value":"active"},"description":{"en":["Example details"]},
       "benefits":{"en":[]},"eligibility":{"en":[]},
       "how_to_apply":{"application_status":"unknown","steps":{"en":[]},
         "documents":[],"notes":[]},"related_ids":[]
     }]}]}

   changing IDs. Wrap each source file's schemes/meta in a collection entry:
   f1_central/central_schemes_master_2026.json -> central;
   f2_tamil_nadu/tamil_nadu_schemes_master_2026.json -> tamil_nadu;
   f3_maharashtra/maharashtra_schemes_app_2026.json -> maharashtra.
   Source ID-map files are not uploaded: canonical IDs match the existing database;
   source_scheme_id creates a verified unique alias and cannot take another ID's
   alias. Existing aliases remain valid even if omitted in a later upload.
   Canonical record IDs use (CEN|TN|MAH|MAHUSR|MAHWEB)2026- followed by exactly
   three digits. central requires CEN prefix, tamil_nadu requires TN, maharashtra
   requires MAH (including MAHUSR/MAHWEB). source_scheme_id, when present, is1..80
   ASCII letters/digits/_/-, starting alphanumeric. level is central|state|
   central_state; status.value is active|unknown|announced|closed.
   Envelope keys are schema_version,mode,collections; each collection entry has
   collection,meta,schemes. Unknown keys at these levels are rejected.
   Use the original name/description/benefits/eligibility language maps, and
   translations.en|ta|hi for the existing localized auxiliary fields. English name
   is required. Absent translations use field-level English fallback. Unsupported
   languages or malformed language values fail validation. Scope must resolve from
   explicit level/state (central + All India is nationwide); unresolved scopes
   are invalid. Related IDs must be unique valid canonical IDs with no self-edge;
   they may refer to existing database records or other records in the upload.
   The full record replaces that scheme's editable payload, not an individual
   JSON-field patch; include translations you want retained for changed records.
   All records are normalized by the existing backend adapter; unsafe application
   links become null and are never fetched. Unknown source metadata remains in raw
   history; only the documented normalized detail fields are exposed to users.
2. Alternative Content-Type:application/zip with the raw ZIP bytes, no multipart.
   Archive contains only dataset.json holding the same envelope. Use a standard
   stored or deflated regular entry without extra fields, comments or descriptors.
   File10MiB; extracted10MiB; max ratio100 with minimum1KiB allowance; one entry.
   Paths, directories, symlinks, encryption, ZIP64, nested archives and other names
   are rejected. No disk extraction or URL downloads.1..2000 records total;
   each record512KiB maximum, nesting40 maximum, no dangerous object keys.
3. Preview200 returns upload_id,valid,new,changed,unchanged,invalid and
   proposed_withdrawals:[]; new/changed/unchanged are canonical ID arrays.
   Invalid records return only safe IDs and error codes, never echoed payloads.
   Invalid envelope/ZIP400; file413; wrong media415. Per-record validation errors
   return a non-stageable valid:false preview. A valid preview writes no schemes
   or drafts. Repeating the same owner/key/content returns replayed:true; a changed
   content with that key409. Fix invalid records and use a new key.
4. Review then POST /v1/admin/schemes/uploads/<upload_id>/stage with JSON {}.
   All changed/new drafts are created in one transaction, or none. Repeating this
   request returns the original drafts (inspect for their current versions).
   Existing open drafts409; stale preview409 SCHEME_PREVIEW_CHANGED; invalid
   preview422 SCHEME_UPLOAD_INVALID. Re-preview after reconciling conflicts.
5. GET /v1/admin/schemes/drafts (max100, after=<last-uuid> for next page) and
   GET /v1/admin/schemes/drafts/<id> to inspect payload plus audit. Direct creation
   POST /v1/admin/schemes/drafts accepts {collection,scheme}. PUT same /<id>
   accepts the full {collection,scheme} with If-Match:"draft-1" from GET ETag.
   Editing clears approval, increments version and records an audit event.
   To withdraw explicitly create {"action":"withdraw","scheme_id":"TN2026-001"}.
   A withdrawal also requires review and publication; no physical row deletion.
6. POST /v1/admin/schemes/drafts/<id>/approve with If-Match:"draft-1" and JSON
   {"note":"Verified source and scope","allow_unreviewed_translation":true}.
   Inspect the exact content/scope/translations/relationships before approval.
   This acknowledges translation limitations rather than claiming certification.
   The returned version/ETag is the approved revision, e.g. "draft-2".
7. POST /v1/admin/schemes/releases, Idempotency-Key:example-publish-key-0001,
   JSON {"drafts":[{"id":"22222222-2222-4222-8222-222222222222","version":2}]}.
   Only selected approved versions publish. Locks serialize editors and legacy
   import/publication operations. Base fingerprints prevent overwriting a newer
   published row. All additions, edits, withdrawals, draft/audit changes, immutable
   release snapshot and latest pointer commit together; any error rolls back all.
   New/edited relationships must target the final published set. Untouched legacy
   links to existing unpublished records are preserved (and remain hidden by RLS),
   so unrelated releases do not require republishing historical data. Include a reviewed edit
   removing an incoming link when withdrawing its target. Aliases cannot transfer.
   Retry uncertain publication with the SAME key and body to recover its response.
   Draft editing/approval/staging and unchanged uploads never create releases.
   To abandon a stale/incorrect open draft, POST
   /v1/admin/schemes/drafts/<id>/discard with If-Match:"draft-N" and
   {"note":"Superseded after source review"}. History remains; create a fresh
   draft from reconciled source. Published/discarded drafts cannot be edited.
   Published metadata cannot be updated/deleted. Version strings are monotonic
   bigint identities, may have gaps on rollback; do not assume consecutive values.
   412 SCHEME_DRAFT_CHANGED: GET/reconcile/reapprove.428: supply quoted precondition.
   409 SCHEME_DRAFT_BASE_CHANGED: create a newly reviewed revision after reconciling
   the competing publication; a stale draft cannot be silently rebased by PUT.
   All admin routes require a server-provisioned admin role;403 must not be retried
   as an ordinary user. Never place database/admin credentials in the mobile app.

New database tables (migration015_scheme_workflow.sql):
- scheme_uploads: owner/idempotency key/content hash and immutable preview inputs;

- scheme_drafts: stable scheme ID, isolated full payload, base fingerprint, optimistic
  version, status, creator/approver/note and timestamps; one open revision per ID.
- scheme_audit: append-only full revision events created/edited/approved/published.
- scheme_publication_receipts: actor/key/request hash/result for publication replay.
- scheme_releases: immutable version/schema/date/count and frozen published snapshot
  built only from scheme tables, including localizations, aliases and relationships.
- scheme_catalog_current: single latest schemes release pointer, updated atomically.
No account data is copied into release snapshots; editorial actor IDs are internal.
Keep audit/upload/receipt retention under an explicit operational policy; do not
delete keys needed to recover retries. Account deletion does not erase editorial

CONVERSATIONAL SAARTHI VOICE
--------------------------
Tap once begins a conversation with explicit selected speech language. Use the
standalone server's GET /v1/voice/stream WebSocket; it proxies Sarvam's documented
Realtime API, not the legacy streaming endpoint or a batch job. No provider key
reaches the app. No saved profile/contact/identity metadata is added to the STT
provider URL or audio messages. First-frame authentication supports browsers, which cannot set
Authorization on WebSockets. CORS_ORIGINS must list an exact approved web origin;
empty configuration permits native clients only. Never add a wildcard.

Wait for ready before capture/transmission. Show partial transcription in-screen,
but only a final or the user's explicit correction may enter grounded POST /chat.
Pause/end/background/navigation close STT and stop capture immediately; audio is
not queued for later replay. Stop the microphone during processing, assistant
playback, screen-reader announcements and correction. Reopen only when the user
has left the conversation running and the previous output has finished. This
half-duplex choice avoids speaker/TalkBack feedback entering the next request.
Interrupt stops playback and invalidates late work before returning to listening.
Always offer text, correction, done-speaking and an obvious pause/end action.
Use1800ms endpoint silence for speakers needing longer pauses;1200ms otherwise.
These are initial settings requiring testing with real speakers, not universal
accessibility or transcription accuracy claims. Never auto-switch the language.

The relay emits one final then closes. Final speech goes through existing owner-
scoped schemeService retrieval; its transaction-local RLS/state scope is preserved.
Speech failure must preserve the text reply. Stream/provider errors preserve
visible partial text for correction, stop the mic and allow explicit retry or
typing. Do not automatically send a partial or loop reconnects on invalid auth,
missing configuration, rate limits, silence or denied browser origin. Refresh
expired access once through the normal shared token-refresh client and reconnect
only if the conversation is still active. Revoked/expired sessions are rechecked
each60 seconds; this bounds rather than eliminates the revocation window.

Resource bounds:5s first-frame authentication,8s provider readiness/finalization,
45s without speech,30s per spoken turn (graceful provider end, never truncating to
a fabricated final),15min session maximum. PCM16 mono16kHz is32000 bytes/second;
base64 to Sarvam adds roughly one third. Relay queues cap at256KB per direction;
input rate64KB/s permits short bursts above normal audio without unbounded replay.
Each process caps32 sockets including unauthenticated connections,4/IP,2/owner;
PostgreSQL enforces30 starts/minute/owner across processes. Increase deployment
capacity only after measuring provider quotas and process memory; process caps
are not a distributed fleet-wide concurrency guarantee. No recordings, transcript,
credentials, raw provider errors or query strings are logged by the relay.

Browser Origin must exactly match CORS_ORIGINS; native clients may omit Origin. HTTP without
Upgrade returns426 WEBSOCKET_REQUIRED. Supported on the standalone Node server, not Vercel

  "access_token": "<latest opaque MSS access token>",
  "language": "ta",
  "silence_ms": 1200
}

{
  "type": "ready"
}

Additional errors:

- 400 INVALID_REQUEST

- 403 VOICE_ORIGIN_DENIED

- 426 WEBSOCKET_REQUIRED / HTTPS_REQUIRED

- 429 VOICE_SESSION_LIMIT (HTTP handshake)

- WebSocket error frame: UNAUTHORIZED / AUTH_TEMPORARILY_UNAVAILABLE / INVALID_VOICE_LANGUAGE
/ VOICE_NOT_CONFIGURED / VOICE_PROVIDER_UNAVAILABLE / VOICE_RATE_LIMITED / VOICE_SESSION_LIMIT
/ INVALID_RECORDING / VOICE_NOT_READY / SILENCE_TIMEOUT / VOICE_FINAL_TIMEOUT /
VOICE_SESSION_EXPIRED / VOICE_CONNECTION_LOST / VOICE_CONNECTION_SLOW

Sample error JSON: {  "error": "INVALID_REQUEST"}

Database tables (including auth/quota dependencies where applicable): mss.auth_tokens,
mss.auth_sessions, mss.users, mss.auth_rate_limits

Usage / client integration:

After ready, send binary PCM16 little-endian mono16kHz chunks2..32000 bytes. First JSON frame
<=4KiB: type,access_token,language,silence_ms only. Explicit language en/ta/hi/mr or matching
-IN locale; silence_ms1200(default) or1800 for longer pauses. Server frames use type: ready,
speech_start, speech_end, transcript.partial/text, transcript.final/text, error/code. Final is
emitted once then the stream closes normally; use existing POST /chat and /voice/speech,
reopening after playback for the next turn. Client {type:finish} gracefully ends input;30
seconds from speech_start also ends input and waits up to8 seconds for final. No speech for45
seconds closes with SILENCE_TIMEOUT. Auth/ready limits5/8 seconds; session15 minutes; token
revalidated each60 seconds. Process caps32 sockets,4/IP,2/owner;30 starts/minute/owner shared
through PostgreSQL; binary ingress64KB/s with64KB burst, queues capped256KB. Do not replay
audio after disconnect. Preserve visible partials for explicit correction if final fails.
Pause/background/reply must close the stream and stop microphone capture; no live mic during
speaker/TalkBack output. Never auto-submit partials or recover by silently enabling language
detection. SARVAM_API_KEY remains only in the backend. See conversational voice guidance
below; these settings are bounds, not measured provider latency guarantees.

28. DELETE ACCOUNT
DELETE /v1/me
==============================================================================================

Purpose: Permanently delete the authenticated Node account and its owned data atomically.

URL: <configured-origin>/v1/me

Authentication / permission: owner bearer; session authenticated within the last 5 minutes

Headers example:

{
  "Accept": "application/json",
  "Authorization": "Bearer <access-token>"
}

Uses only the token owner. Access-token refresh does not count as recent authentication.

Sample JSON request:

No body.

Success HTTP: 204

Sample response:

No JSON success body.

204 has no response body. All account sessions and access/refresh tokens are deleted;
subsequent calls with them return 401.

Additional errors:

- 400 INVALID_ACCOUNT_DELETION_REQUEST

- 401 UNAUTHORIZED (including expired/revoked/rotated token or already deleted account)

- 403 REAUTHENTICATION_REQUIRED

- 429 ACCOUNT_DELETION_RATE_LIMITED (3 attempts/minute/owner, Retry-After)

- 503 ACCOUNT_DELETION_UNAVAILABLE (missing migration/grant or database failure; no successful
deletion acknowledged)

Sample error JSON: {  "error": "INVALID_ACCOUNT_DELETION_REQUEST"}

Database tables (including auth/quota dependencies where applicable): mss.users, mss.profiles,
mss.startup_profiles, mss.legal_acceptances, mss.onboarding_requests, mss.notifications,
mss.password_credentials, mss.user_roles, mss.login_codes, mss.auth_sessions, mss.auth_tokens,
mss.support_tickets, mss.favorites, mss.eligibility_results, mss.notification_event_heads,
mss.notification_events, mss.push_devices, mss.notification_push_jobs,
mss.notification_publish_receipts, mss.auth_rate_limits

Usage / client integration:

After explicit user intent to delete, send DELETE /v1/me with a current bearer and no body. On
403 perform fresh Google sign-in or existing password login, then retry deliberately with the
new token (refresh alone is insufficient). On 204 clear all local tokens/private
caches/offline snapshots and return to signed-out state. Linked support tickets are
hard-deleted with the account; guest tickets are not selected by unverified matching email.
Temporary hashed anti-abuse counters remain until normal expiry/cleanup. This affects only
Node-owned data, not the Google account or unmigrated Supabase/external records. Signing in
after successful deletion creates a new empty account. After an uncertain network response, do
not automatically sign in/recreate an account. Deploy migration012_account_deletion.sql and
DELETE-on-users runtime grant before enabling. Fail-closed schema guard rejects the old
support SET NULL foreign key. Source/local tests do not certify live rollout.
