# Internationalization — two separate systems, not one

The mobile app has **two distinct localization mechanisms** that are easy to conflate. A web port needs both, kept separate the same way the app keeps them separate.

## System 1: UI string localization (ARB → your i18n library)

Every static UI string ("Search schemes, benefits...", "Continue", "Complete Your Profile") comes from `frontend/lib/l10n/app_en.arb` / `app_ta.arb` — flat key→string maps, accessed in Dart via `context.l10n.<key>`.

**Web equivalent**: use `next-intl` (or `next-i18next`) with JSON message catalogs mirroring the same keys where practical:

```
messages/
├── en.json
└── ta.json
```

```json
// en.json
{
  "search.placeholder": "Search schemes, benefits or ask...",
  "profile.continueButton": "Continue"
}
```

You don't need to reuse the exact same key names as the ARB files (`navContinueButton` vs. `profile.continueButton`) — pick a convention that fits `next-intl`'s namespacing (dot-notation by feature area reads well). What matters is **1:1 coverage**: every user-visible string gets a key in both `en.json` and `ta.json`, the same discipline the mobile app enforces (never hardcode a string directly in a component — the main repo has a dedicated test guarding this).

## System 2: Catalog content localization (per-entity, NOT ARB)

Scheme names, benefits, overviews — anything that comes from the **catalog data itself** — is localized differently: each catalog entity carries its own `localization.<lang>.<field>` sub-object (02-DATA-MODEL.md §1). This is deliberate and documented as intentional in the main repo's memory: *"catalog content stays out of ARB by design."*

**Do not put scheme names/benefits/etc. into your `en.json`/`ta.json` message catalogs.** Read them from the catalog entity's own `localization` object at render time, using the same lookup-order fallback as the app:

```
localization[currentLang][field] → localization.ta[field] → localization.en[field] → ''
```

Getting this backwards (routing catalog content through the UI-string i18n library) means every new scheme or scheme edit requires a code deploy to add its translated strings — the whole point of the per-entity `localization` object is that catalog updates don't require a redeploy.

## Locale routing

Two common Next.js patterns work here — pick one and note the choice in the new repo's README:

- **Path-based** (`/en/search`, `/ta/search`) via `next-intl`'s `[locale]` segment — better for SEO (11-SEO.md), since each language gets its own indexable URL.
- **Cookie/session-based** (single URL, language switched via a stored preference) — closer to how the mobile app behaves (one app, language is a setting, not a URL), simpler to build first.

If SEO matters for the public-facing scheme-discovery pages (it likely does — see 11-SEO.md), lean path-based for at least the scheme detail and discover pages, even if the rest of the site (auth, profile, settings) stays cookie-based.

## Known trap to avoid replicating

The mobile app had a real, fixed bug this session where a language *setting* (`AppProvider.selectedLanguage`) and the actual rendered UI locale could desync — one screen stuck showing the old language after a switch, because it read the setting via a non-reactive provider call inside a kept-alive tab (see the main repo's `docs/audit/AUDIT.md` §0, bug #1). The web equivalent risk: a locale value cached in a React context or `localStorage` that a component reads once (e.g. in a `useEffect` with an empty dependency array) rather than subscribing to changes. Use `next-intl`'s reactive locale context (or equivalent) everywhere, not a one-time read, so a runtime language switch actually propagates to every mounted component.

## Fonts per locale

From 01-DESIGN-SYSTEM.md: English uses Poppins (headings) + Inter (body); Tamil uses Arima (accents) + Noto Sans Tamil (body). Load both font families via `next/font/google` and switch the applied `font-family` class based on the active locale, rather than loading only one font family and hoping it has adequate Tamil glyph coverage (most don't).
